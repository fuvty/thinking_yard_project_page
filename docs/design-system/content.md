# 内容与中英文写作规范

适用于首页及项目页面。目标是准确、清晰、自然，让读者理解研究思路与贡献。篇幅服务于理解，不以越短越好为目标。本文维护写作与事实原则；排版与多语言实现见 [视觉基础](foundations.md) 和 [多语言维护](../localization.md)。

## 从讨论到页面

- 用户提供的说法通常是思想、例子或方向，不是待粘贴的定稿。先理解意思，再组织成适合公开页面的表达。
- 不把讨论过程、修改说明、实现细节写成页面正文。
- 简洁不等于省略逻辑。保留必要的因果、概念区别和例子，删除重复铺垫、空泛总结，以及对标题的反复解释。
- 原本清楚的一段不必强行缩短。较长的两段优先检查是否重复，可合并，但不要给每节规定相同的句数或字数。
- 表达应连贯自然。避免用 `--`、长破折号串联句子；需要转折或补充时，用自然的连接词或另起一句。

## 中英文各自成文

- 两种语言各自成文，保持核心观点、事实和限定条件一致，不要求逐句对应。先理解研究对象、机制和比较关系，再用目标语言重新组织；不能把明确的技术贡献改成笼统的效果。英文原文不清楚时，也应同步修订。
- 中文用自然、明确的表达，避免翻译腔和人为压缩的口号。例如写“提升智能的三条路径”，而不是“提升智能，三条路径”。
- 保留有助于准确理解的术语，如 test-time compute；不要为显得专业而增加术语或重复中英括注。
- 加粗、强调色与局部渐变必须对应同一个概念或数据，不能随着语序改变而换成另一个重点。例如 AKV 的 cache engineering 对应“缓存工程”，而非“推理服务系统”。
- 写作与排版分别验收：先单独读中文，确认自然流畅；再在实际页面检查断行。不能为了凑齐两行而删掉限定条件，也不能以“翻译准确”代替阅读体验。
- 标题说明观点，正文补充机制、条件或例子。不要让眉题、标题和正文连续说三遍同一件事。

## 数字与研究结论

- 修订前核对论文版本与具体表格。每项数字要能追溯到指标、基线和实验范围；首页并列指标优先使用同一设置，并用简短说明标明范围。论文摘要与表格口径不一致时，明确采用哪一组证据，不混用或猜测。
- 单位与聚合方式属于结论的一部分。准确率差值用“百分点 / pp”，区别于相对提升百分比；生成速度区别于请求延迟，训练集标签比例区别于部署调用率。“比值的平均”与“平均值的比”也不能互换。
- 事实修订必须同步中英文的数字、单位、基线、限定条件和动态摘要，不能只改一种语言或首页大数字。无需因文案调整改写正确的原始数据。具体核对结果留在研究记录中，设计原则不固定某篇论文的当前数值。

## 首页的研究叙事

三条路径的区别应始终清楚：

1. **沿现有路径增加投入，提升上限。** 参数、数据、推理投入是例子，也应交代收益递减带来的成本增长。
2. **提高效率，以更低成本获得相近能力。** 可用量化、稀疏注意力、推测解码、自适应计算说明；正文解释研究意义，不描述“绿色曲线逐点变形”等动画实现。
3. **寻找新的提升维度。** 可用 o1 与 test-time compute 帮助理解。循环深度、自适应计算、上下文信息密度等是探索方向，不是封闭或完整的清单。不要把历史概括成“以前只有两个维度”。

项目介绍体现“在算法、系统等多层次联合优化”，不要改写为“把想法落地为系统”。图表纵轴使用 intelligence；首页路径三不展示原先的预算分配公式。

## 项目内容与维护

- 术语统一写作 `KV cache`：KV 大写、cache 小写，以空格分隔，不使用连字符。英文复数按语法写作 `KV caches`。AKV 的简介强调让执行长程任务的智能体自行管理 KV cache。
- 以团队研究为中心，避免不必要的个人主页式介绍。保留准确的作者、贡献标记和资源信息。
- 不添加“项目页包含论文、代码和演示”等显而易见的说明，不恢复模板借用声明或原始数据下载入口。
- 项目简介明确研究对象和贡献；数字、结论与链接应有来源，尚未公开的资源不猜测。
- 首页正文和图表说明统一维护在 `hub/locales/en.json`、`zh.json`。项目名称、分类、路线、简介及可选中文译文维护在 `config/projects.json`，不要复制另一份项目清单。
- 项目页共用 HTML 结构和交互脚本，中文文案独立维护，公共控件统一翻译。按 [多语言验收流程](../localization.md#验收流程) 核对内容、排版和交互。

本规范记录写作原则，不冻结当前措辞。后续内容按研究事实和最新反馈调整。
